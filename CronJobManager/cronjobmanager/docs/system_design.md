# 定时任务调度器系统设计文档

## 1. 概述

本文档描述了定时任务调度器（CronJobManager）的系统架构设计，包括系统架构、模块设计、数据模型、关键流程设计等内容。

## 2. 系统目标

本系统旨在提供一个功能完善的Python定时任务调度器，满足以下需求：

1. 支持Cron表达式定义任务执行时间
2. 支持一次性任务和周期性任务
3. 支持任务依赖关系配置
4. 提供任务执行日志记录和查询
5. 支持任务失败重试机制
6. 提供任务执行状态监控和告警通知
7. 支持同时运行至少50个定时任务

### 5.3 失败重试机制

**重试策略**：

1. **重试次数**：由 `max_retries` 配置
2. **重试间隔**：初始间隔由 `retry_interval` 配置
3. **退避策略**：指数退避，公式为：
   ```
   sleep_time = retry_interval * (backoff_factor ^ (retry_count - 1))
   ```

**重试流程**：

```
任务执行失败
      │
      ▼
重试次数+1
      │
      ▼
检查是否超过最大重试次数
      │
┌─────┴─────┐
│           │
是          否
│           │
▼           ▼
最终失败    计算等待时间
触发告警      │
│           │
▼           ▼
结束      等待指定时间
              │
              ▼
         重新执行任务
              │
              ▼
         返回结果
```

## 6. 性能设计

### 6.1 并发设计

- **线程池执行器**：使用 `ThreadPoolExecutor` 执行任务
- **最大并发数**：默认100个线程，可配置
- **任务隔离**：每个任务在独立线程中执行
- **任务状态隔离**：任务间状态互不影响

### 6.2 资源管理

- **数据库连接池**：SQLAlchemy自动管理
- **任务结果不持久化**：避免内存泄漏
- **日志轮转**：自动清理旧日志

### 6.3 性能指标

- **同时运行任务数**：至少50个（配置可达100个）
- **任务启动延迟**：< 1秒
- **任务调度精度**：取决于系统和APScheduler

## 7. 安全设计

### 7.1 数据安全

- **SQL注入防护**：使用SQLAlchemy ORM，参数化查询
- **任务函数验证**：函数路径必须使用 `module.function` 格式

### 7.2 异常处理

- **全面的异常捕获**：所有任务执行都有异常处理
- **详细的错误日志**：记录错误信息和堆栈跟踪
- **优雅降级**：任务失败不影响调度器运行

### 7.3 资源限制

- **任务超时**：支持配置任务执行超时
- **重试限制**：限制最大重试次数，防止无限重试

### 9.4 作业持久化方案说明

#### 方案对比分析

在选择作业持久化方案时，调研了以下几种方案：

| 方案 | 优势 | 劣势 | 适用性 |
|-----|------|------|--------|
| **SQLAlchemyJobStore (APScheduler 3.x)** | APScheduler官方支持，完整的作业持久化 | 与SQLAlchemy 2.0+存在pickle序列化兼容性问题，无法正常工作 | ❌ 不适用 |
| **APScheduler 4.x (Alpha版本)** | 改进了SQLAlchemy 2.0支持 | 仍为Alpha版本，API不稳定，存在未知风险 | ❌ 不建议生产使用 |
| **自定义JobStore** | 完全可控，可精确控制持久化逻辑 | 开发成本高，需要维护APScheduler内部API兼容性 | ⚠️ 可选但成本高 |
| **MemoryJobStore + 数据库恢复** | 简单可靠，规避兼容性问题，任务定义和日志完整持久化 | 运行时作业状态（如下次执行时间）重启后丢失 | ✅ 当前选择 |

#### 当前方案

本项目选择 **MemoryJobStore + 数据库恢复** 方案，采用以下持久化策略：

1. **任务定义持久化**：所有任务的配置信息（名称、函数路径、调度策略、重试配置等）持久化到SQLite数据库
2. **执行日志持久化**：所有任务执行记录持久化到SQLite数据库
3. **APScheduler作业管理**：使用MemoryJobStore存储运行时作业状态

#### 启动恢复机制

调度器启动时会自动从数据库加载所有启用的任务并重新注册到APScheduler，确保重启后任务能够继续执行。

#### 局限性说明

当前方案存在以下局限性：

1. **作业运行时状态丢失**：
   - 重启后，APScheduler中的作业对象（包含下次执行时间、最后执行时间等运行时状态）会丢失
   - 任务会根据调度策略重新计算下次执行时间
   - 这意味着如果任务原本应该在重启期间执行，而重启后错过了执行窗口，可能无法触发

2. **并发执行状态不持久化**：
   - 如果重启时任务正在执行，任务会被中断
   - 需要依赖任务自身的幂等性设计来保证数据一致性

3. **作业计数器重置**：
   - APScheduler内部的作业执行计数器在重启后会重置
   - 但执行日志仍会完整保存在数据库中

#### 方案选择理由

选择当前方案的主要原因：

1. **稳定性优先**：APScheduler 4.x仍处于Alpha阶段，不建议在生产环境使用
2. **开发成本**：自定义JobStore需要深入了解APScheduler内部实现，维护成本高
3. **核心数据完整**：任务定义和执行日志这两类核心数据已完整持久化到数据库
4. **可接受的局限性**：对于大多数场景，运行时作业状态的丢失是可接受的

#### 未来改进方向

待APScheduler 4.x稳定版本发布后，可以考虑升级以获得更好的SQLAlchemy 2.0支持，届时可以切换回SQLAlchemyJobStore获得完整的作业持久化能力。

## 10. 扩展设计

### 10.1 可扩展点

1. **告警通道扩展**：可添加钉钉、企业微信、Slack等告警
2. **执行器扩展**：可添加ProcessPoolExecutor、TornadoExecutor等
3. **JobStore扩展**：可添加Redis、MongoDB等存储
4. **触发器扩展**：可添加自定义触发器

### 10.2 监控集成

- **健康检查**：提供调度器状态查询
- **任务状态**：提供任务列表和状态查询
- **执行统计**：提供任务执行统计信息

## 11. 故障处理

### 11.1 常见故障

| 故障场景 | 处理方式 |
|----------|----------|
| 任务函数加载失败 | 记录错误日志，跳过执行 |
| 任务执行超时 | 记录超时日志，标记为TIMEOUT |
| 数据库连接失败 | 重试连接，记录日志 |
| 调度器重启 | 自动恢复所有启用的任务 |
| 依赖任务失败 | 根据依赖条件决定是否执行后续任务 |

### 11.2 数据恢复

- **任务恢复**：启动时自动恢复所有启用任务
- **日志保留**：可配置日志保留天数
- **数据库备份**：定期备份SQLite数据库文件
